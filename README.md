# 51-MCU-Code-Template

这是一个用来存放 **51 单片机（STC89C52 / AT89S52 等 8051 内核）** 代码模板的仓库。

所有模板都遵循同一个目标：**把"能跑就行"的代码，拆成"换个工程就能直接套用"的模块**。

**每个模块的详细文档都放在各自目录的 `README.md` 里**（实现解析、移植指南、扩展路线、资源占用、使用边界）。本文件只做三件事：**模块索引**——仓库里有什么、各占什么资源，一张总表说清，避免新工程里撞车；**快速上手**——想干什么、去查哪一节；**写法约定**——贯穿所有模块的分层与命名规则，贡献新模块时照此对齐。

三个模块**可以独立使用，也可以组合使用**：KEY 消抖靠 Delay 提供的毫秒节拍（见 [KEY README](./KEY模块_P1.4~P1.7_按下为低/README.md) 的「扩展路线 · 加消抖」）；KEY 选图案、LED 出画面则是三模块联动的最小示范（见下文「模块组合」与 [LED README](./LED模块_P0P2_低电平点亮/README.md) 的「扩展路线 · 与按键联动」）。

> **关于 Timer1**：Delay 模块的节拍源不在本仓库中，请使用你自己的定时器模块。
> 它只需对外提供两个接口：`Timer1_Init()`（启动 1ms 节拍）与 `Timer1_GetTick()`（读毫秒计数），
> 寄存器级配置见 [Delay README → 寄存器速查](./Delay模块_Timer1节拍驱动_差值毫秒延时/README.md)。
>
> **关于寄存器头文件**：`KEY.c` 与 `LED.c` 用 `<REGX51.H>`，Delay 示例用 `<REGX52.H>`。二者都能编译通过
> （`REGX52.H` = `REGX51.H` + Timer2 寄存器），但同一工程内建议**统一成一个**，避免混用带来的困惑。
>
> **关于 P0 口**：LED 模块占用了 P0 口。P0 是开漏输出、**没有内部上拉**，接 LED 时必须外接
> 4.7k~10k 上拉排阻，否则"写 1 熄灭"不可靠 —— 这是 51 平台的经典坑，
> 详见 [LED README](./LED模块_P0P2_低电平点亮/README.md)。

**硬件资源速记**

- **Delay**：Timer1（模式 1，16 位定时，中断号 3 / 向量 0x1B）+ ET1/EA + 约 5B RAM；**GPIO 占用为零**。
- **KEY**：P1.4~P1.7 共 4 个 I/O，**低电平 = 按下**；不占定时器、不占中断、约 1B RAM。
- **LED**：P0.0~P0.7 + P2.0~P2.7 共 16 个 I/O（DIP40 第 32~39、21~28 脚），**低电平 = 点亮（写 0 亮）**；不占定时器、不占中断；两张图案表约 12B ROM（`code` 区）+ 约 1B RAM。**P0 必须外接 4.7k~10k 上拉排阻**（开漏无内部上拉）。
- 三模块组合时：16（LED）+ 4（KEY）= 20 个 I/O + Timer1 + ET1/EA + 约 8B RAM。
  8051 的 32 个 I/O 里除 LED 占的 16 个、KEY 占的 4 个、串口下载占的 P3.0/P3.1 之外，还有 10 个可用；
  Timer0、Timer2 以及串口以外的中断与优先级资源全部空闲，**三模块无资源竞争**。
  唯一要留意的是 P0/P2 已被整口占用：数码管（P0 段选 + P2 位选）、点阵屏等显示类模块需让位或分时复用
  （见 [LED README「扩展路线 · 端口让位」](./LED模块_P0P2_低电平点亮/README.md)）。

## 一、写法约定（所有模块共同遵守）

### 1. 三层分工

| 层次 | 职责 | 本仓库示例 |
|------|------|-----------|
| 应用层 | 业务逻辑（点灯、菜单、游戏控制…） | `main.c`（由使用者自建） |
| 驱动 / 服务层 | 把硬件能力封装成纯软件接口 | `Delay.c`：`DelayMs(500)`<br>`KEY.c`：`Key()` → 键号<br>`LED.c`：`LED_SetPattern(LED_PAT_A)` → 图案画面 |
| 硬件配置层 | 寄存器级初始化与中断服务 | 你的 `Timer1.c`：`Timer1_Init()` + ISR |

模块之间**只通过 .h 中声明的函数通信**，绝不跨模块直接读写寄存器或共享全局变量。

### 2. 接口最小化

三个模块的对外声明一共三行（外加 LED 的图案编号枚举）：

```c
void          DelayMs(unsigned int ms);           /* Delay.h：阻塞延时约 ms 毫秒 */
unsigned char Key(void);                          /* KEY.h：扫一次按键，返回 0~4 */
void          LED_SetPattern(unsigned char pat);  /* LED.h：显示编号 pat 的图案 */
```

调用者不需要知道节拍从哪来、误差多大、按键接在哪个引脚、是高有效还是低有效、LED 接在哪两个口、是高电平还是低电平点亮 —— 这正是"可套用"的前提：**接口越窄，被替换 / 升级时波及的代码越少。**

### 3. 单向依赖

```text
                      ┌──> Delay（服务层）──> Timer1（硬件层）
                      │        不回调            不认识 Delay
应用层 main.c ────────┼──> KEY（服务层）───> P1.4~P1.7（直接寄存器）
                      │        不认识 Delay，也不认识 main
                      └──> LED（服务层）───> P0、P2（直接寄存器）
                               不认识 KEY，也不认识 main
```

下层永远不知道上层的存在。因此 `Timer1` 可以同时喂给 Delay、按键消抖、PWM、串口超时等任意多个模块；`KEY` 与 `LED` 也可以被任意业务调用，且**删掉 Delay 模块，KEY、LED 照常工作**（KEY 只是失去消抖手段，LED 本来就不依赖它）。

### 4. 厚模块 vs 薄模块：允许合并层次

| | **Delay**（厚模块） | **KEY**（薄模块） | **LED**（薄模块） |
|---|---|---|---|
| 是否依赖其他模块 | 是，依赖 Timer1 节拍 | 否，自给自足 | 否，自给自足 |
| 是否操作寄存器 | **完全不操作**（纯算法） | 直接读 `P1_4~P1_7` | 直接写 `P0`、`P2` 整口 |
| 硬件绑定点 | 收敛在 `Timer1_GetTick()` 这一个函数名 | 收敛在顶部 4 行 `#define` | 收敛在两张图案表 + 函数内两行赋值 |
| 分层是否完整 | 服务层 / 硬件层严格分离 | 两层合并（模块太薄，分开反而累赘） | 两层合并，且多一层"数据表"间接 |

`KEY.c` 同时扮演服务层和硬件层，按纯粹的分层原则它应该再拆一层（例如 `GPIO_ReadPort1()`）。但对于只有十几行、没有初始化、没有状态的模块，**强行拆层只会增加文件数量，不会增加可维护性**。判断标准是：*硬件绑定点是否收敛在一处、是否能一眼改完*。模块变厚（要加消抖、边沿检测、矩阵扫描）时，再把引脚读写下沉到独立的 GPIO 层也不迟 —— 详见 [KEY README 的扩展路线](./KEY模块_P1.4~P1.7_按下为低/README.md)。

`LED.c` 是薄模块的另一种形态：它把"新图案"从**改代码**变成**改数据** —— 显示逻辑（两行整口赋值）永远不变，图案全部长在两张 `code` 表里，加一种图案只是表尾各添一个字节。数据驱动让"薄"和"可扩展"不再矛盾，越界保护则收敛成统一出口（越界一律回退全灭）—— 详见 [LED README](./LED模块_P0P2_低电平点亮/README.md)。

## 二、三模块组合：一个典型 main.c

```c
#include <REGX52.H>
#include "Timer1.h"
#include "Delay.h"
#include "KEY.h"
#include "LED.h"

void main()
{
    unsigned char key;
    unsigned char pat = LED_PAT_ON;

    Timer1_Init();          // 必须先启动节拍源，否则 DelayMs 永不返回
    LED_SetPattern(pat);    // 开机先给一个确定画面（P0 记得接上拉排阻）
    while (1)
    {
        key = Key();        // 扫一次按键：0=无键，1~4=键号
        if (key != 0)
        {
            DelayMs(20);    // 消抖：跨过机械触点的抖动窗口
            if (Key() == key)   // 复查：20ms 后仍是同一个键才算真按下
            {
                pat = (unsigned char)((pat + 1) % LED_PAT_NUM); // 切到下一个图案
                LED_SetPattern(pat);   // KEY 负责输入，LED 负责输出，main 只做翻译
                while (Key() != 0); // 等松手，避免一次按下被重复计数
                DelayMs(20);        // 松手也抖，同样消抖一次
            }
        }
    }
}
```

> 这段代码演示的是**最朴素的阻塞式按键处理**，胜在直观。它会占用 CPU（`while(Key()!=0)` 期间主循环停摆），
> 若主循环还要刷数码管 / 跑串口，请改用非阻塞扫描，见 [Delay README 的 DelayCheck()](./Delay模块_Timer1节拍驱动_差值毫秒延时/README.md) 与 [KEY README 的非阻塞定时扫描](./KEY模块_P1.4~P1.7_按下为低/README.md)
> （刷数码管前记得先解决 P0/P2 与 LED 模块的端口冲突，见 [LED README「扩展路线 · 端口让位」](./LED模块_P0P2_低电平点亮/README.md)）。

硬件上：KEY 占 P1.4~P1.7，LED 占 P0、P2 两个整口（P0 需上拉排阻），Delay 靠你的 Timer1 出 1ms 节拍 —— 三个模块拼在一起仍无资源竞争。

## 三、贡献模板的规范（供后续新增模块参考）

- 一个模块一个目录：一对 `.c/.h` **+ 一份模块级 `README.md`**（写清实现解析、移植指南、扩展路线、资源占用、使用边界，可参照现有三个模块的 README）；
- 目录名沿用 `功能_外设或引脚_特性` 格式；
- `.h` 中写清**前置条件**（如"须先 Init"）与**资源占用**；
- **硬件绑定点必须收敛**：要么只出现在硬件配置层（如 Delay 只认 `Timer1_GetTick()` 一个函数名），要么集中在文件顶部连续的几行 `#define`（如 KEY 的 4 行引脚定义）或一两处数据表 + 赋值（如 LED 的两张图案表 + 两行整口写）；服务层其余代码不得出现寄存器名；
- 模块足够薄时（无初始化、无状态、十几行），允许服务层与硬件层合并，不必强行拆分 —— 判据是"改起来是否一目了然"；
- 每个模块的 README 必须附带一节"改哪里能得到什么"的移植 / 扩展说明；
- 新增模块后，同步更新**本文件**的模块索引、目录结构、TL;DR 表与硬件资源速记。
